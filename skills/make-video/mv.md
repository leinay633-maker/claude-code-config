# 做 MV：程序生成画面（mv-engine）

用户给一首歌要做 MV 或歌词视频、画面全部由代码生成时，按这份做，不加载 HyperFrames。拿现成图片、视频卡点剪的，走 HyperFrames 的 `music-to-video`。

## 东西在哪

- 引擎是 [mv-engine](https://github.com/leinay633-maker/mv-engine)（改自开源项目 pdoom-video，MIT），下文的 `<ENGINE>` 指它的本地克隆。`app/` 是渲染器，`analysis/` 是分析脚本，`new-project.ps1` 建工程，`analyze.ps1` 跑分析。只在要改引擎本身时动模板。安装和依赖见它的 README。
- 每支片子一个独立工程。场景 API 在工程的 `docs/ENGINE.md`；创作依据写在工程的 `docs/TREATMENT.md`，模板是 `docs/TREATMENT.template.md`。

## 六步

### 1 交代任务

- 定下：哪首歌、哪个版本，音频文件，歌词文件（LRC，可选译文和逐字 YRC），画幅（横 16:9 或竖 9:16），时长（默认整首），发到哪。用户的话能推出来的直接定，推不出来的才问。
- 音频用用户给的文件；没有就停下问，加密格式不破解。
- 建工程：`<ENGINE>/new-project.ps1 -Name <英文名> -Audio <音频文件> -Title <片名> -Root <工程根目录> [-Aspect 9:16]`。母带会转成 48 kHz WAV。脚本不装依赖，进工程的 `app/` 跑 `bun install --frozen-lockfile`。
- 交付的是能跑的工程、浏览器预览和成片，不是只交一份创意方案。

### 2 对时间

- `<ENGINE>/analyze.ps1 -Project <工程目录> -Lrc <歌词.lrc> [-Tr <译文.lrc>] [-Yrc <逐字.yrc>]`。顺序是导入歌词、分轨、节拍和段落、逐字对齐、裁字体。第一次跑会下载对齐模型。
- 逐字时间用声学对齐（中文转拼音、日文转罗马字）；有 YRC 的句子直接用 YRC。对不上的句子会退回按音节估算，并在报告里标出来。
- 看 `work/audio-report.md`：BPM、速度是否恒定、小节相位把不把握得住、段落。在 `data/audio.json` 里把段落名改成 intro、verse1、chorus1……
- 分不出哪拍是强拍、或者恒速歌被判成变速时，自己定 BPM 和第一个强拍再跑：`-Steps audio -AudioArgs @('--bpm','130','--downbeat','0.248')`，得到的是不再搜索的恒速网格。
- 看 `work/lyrics-report.md`：LRC 偏移，每句用的方法和分数。被标记的句子要在预览里逐句听。长音、和声、叠唱最容易错，上一句拖长音时，下一句的开头常被对到拖音上。不对就写 `work/lyrics-fix.json`，再跑 `-Steps align,fonts`。
- 歌词错字、自己翻译的中文，改 `work/lines.json`。
- 拿不准的地方列出来交给用户，不要自己猜。

### 3 统一风格（方案先给用户确认）

- 把 `docs/TREATMENT.template.md` 复制成 `docs/TREATMENT.md`，照着写：一句话设定、贯穿母题、配色（三种颜色加一个只用一次的点缀）、字体分工、细节从哪来、禁用清单、逐场表。用户给了参考图就一起看。
- 交给用户之前先自查两条：
  - 设定是一个点子，还是一串场景？歌词有没有变成视觉双关或变形，还是唱什么画什么？
  - 每一场的细节从哪来（排线、线描、网点、纸纹……）？有没有用到禁用清单里的东西？
- 审美由用户拍板。定下来以后，配色写进 `app/project.json` 的 `palette`；中日文字体写进 `cjkFonts`，再跑 `-Steps fonts`。

### 4 让歌词决定动作

- 逐场表里每一句都写清：情绪、文字怎么动、镜头怎么走、和前后怎么接。关键动作落到具体的词（`lyrics.span(line, '词')`）和拍点上。
- 每次转场写明上一镜留下什么、下一镜把它变成什么；同一个元素换一种用法，把不同场景串起来。

### 5 做成动画（先做一个场景）

- 主会话按逐场表写 `app/src/timeline.ts`，切点锚到歌词和强拍，不写死秒数。
- 先做最有代表性的一个场景。截帧、出联系表、跑细节测量，把静帧或预览给用户看，方向确认了再铺开。
- 全片统一的画法（光标、大写词砸入、反复出现的角色、计量条）先由主会话写成公共模块，场景只引用，避免各场各画一套。
- 方向确认后，其余场景可以交给子代理（分工见 SKILL.md「约定」）。任务说明里附上本文「坑」。每场写完都要截帧、看图，跑 perf 和 fineness。

### 6 检查修改，再导出

- 每一场都要过：`stills` 截关键时刻，`sheet --cuts` 看切点前后，`perf` 看每帧耗时，`analysis/fineness.py` 测细节。edge% 低于 5 或 smooth% 高于 25，就回头加纹理；line% 远超 40，多半是满屏铺了同一种纹理，要留出黑的负空间。数字只作参考，局部裁图也要看。
- 带音乐播放预览：有没有字亮早了、被挡住、出了安全区，动作有没有落在拍上。
- 用户提了意见只改那一处，其他保持不变；小问题攒一批再改，不要一条一渲。
- 全片过完、用户点头后只渲一次：在工程的 `app/` 里放后台跑 `bun run render video --samples auto --shutter 0.2`。渲完核对：时长；音轨和母带的偏移（包络互相关）；峰值；抽 10–20 帧和预览对照。
- 工程保留，方便以后接着改。

## 画面要细

- 表面用排线、线描、网点等纹理画；平滑渐变和散景只占一小部分，模糊只用于景深。
- 线宽 1–1.5 px，边缘锐利；只有主色发光，白字不发光、不加光晕和描边。
- 每帧三层尺度：大字、主体、小号注释或纹理；颗粒由后期统一加。
- 每段可以换画法，但配色、字体、发光规则全片统一。“华丽多变”要靠细节和构图变化撑，不靠堆现成特效。

## 坑

- 无头 Chrome 必须用上真显卡：`bun run render gpu` 的输出里不能出现 SwiftShader。
- 往 sRGB 纹理里传 Canvas2D，Windows 上的 Chrome 会绕道 CPU，1080p 每层每帧 20 多 ms，开运动模糊时成片慢几十倍。自己建 `CanvasTexture` 不要设 `SRGBColorSpace`。
- Canvas2D 的 `blur()` 和 `shadowBlur` 很慢，还会把画面弄糊。发光走 HDR：线条颜色给到大于 1，或画在第二层再叠加。
- 画面上新加了中日文字要重跑 `-Steps fonts`，不然缺的字会回落到系统字体。
- 场景里不写死秒数，歌词时间只认 `data/lyrics.json`。
