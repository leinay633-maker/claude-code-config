# MV 工程进程清理与着色器编译

## 截帧后的开发服务

截帧脚本若启动了中间运行器和开发服务，只结束直接子进程可能留下真正的服务进程。正常退出、中断和失败都要覆盖清理。

- 清理前核对命令行、父子关系和工程归属；只处理属于当前任务的 PID，不按 `node` 进程名批量结束。
- 检查脚本启动的完整进程树，不能把中间运行器退出当作服务已退出。
- 旧工程的脚本可能与当前模板不同；使用前检查清理逻辑，不假定模板修复会自动传播。

## 着色器编译白屏

复杂场景首次打开白屏时，区分资源加载、编译等待和运行错误。先检查日志并分别测量编译耗时与单帧耗时。

- 某些编译后端会内联复杂函数或展开循环。多个距离场调用点可能放大编译量；先确认调用结构再优化。
- 减少重复调用时保留必要的材质和命中信息，避免只为取一个结果又算一次完整场景。
- 常量表、动态索引和循环改写可能改善编译却拖慢每帧运行；分别实测，不把某种技巧设为通用必选项。
- 测速前关掉属于本任务的空转预览，确认暂停状态是否仍在重画。
- 不把特定后端的耗时数字、补丁状态或旧工程名单写成其他环境的结论。
